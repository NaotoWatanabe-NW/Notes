# 設計書（docs/design/）

コードを書くときは設計書を残して、**意図と全体像をあとから追跡できるようにする**（ユーザーの方針）。
このフォルダはその置き場所。1つの設計判断（またはひとまとまりの変更）につき1ファイルを書く。

## SPEC.md との役割分担

| | `docs/SPEC.md` | `docs/design/NNNN-*.md` |
|---|---|---|
| 何を書くか | **いまの仕様**。何がどう動くか、API・データモデル・画面の約束 | **なぜそう決めたか**と全体像。選ばなかった案、移行の手順、残っている課題 |
| いつ直すか | 実装と同じコミットで、常に現状に合わせて書き換える | 採用したら本文の「決定」は書き換えない。方針が変わったら新しい番号で書く |
| 読む人 | 使い方・振る舞いを知りたいとき | 「どうしてこうなっているのか」「どこから変わったのか」を知りたいとき |

- SPEC の該当箇所からは設計書へリンクを張る（例: 「→ `docs/design/0001-storage-boundary.md`」）。
  SPEC に理由を長々と書かず、理由は設計書に寄せる。
- 保存方針の上位文書 `Storage/_vault/document-storage-policy.md`（リポジトリ外）がある場合、
  設計書はそれを Notes アプリでどう具体化したかを書く。

## いつ書くか

- 複数のファイル・モジュールにまたがる変更
- データの置き場所・形式・持ち主を変える変更（DB の列、ファイルの形式、frontmatter など）
- あとから「なぜこうなっているのか」と聞かれそうな判断
- 小さなバグ修正や文言の修正には書かない

設計書は実装の前に書き、coder は設計書だけを読んで実装できることを目標にする。

## 命名規則

`NNNN-短い英語名.md`

- `NNNN` は4桁の連番（0001 から）。番号は再利用しない（却下・置き換えになっても欠番にしない）
- 英語名は小文字の kebab-case で、内容が分かる2〜4語（例: `storage-boundary`, `author-notes`）
- 本文は日本語

## 状態

| 状態 | 意味 |
|---|---|
| 提案 | 検討中。まだ実装に入らない |
| 採用（未実装） | 決定済み。実装待ち |
| 実装済み | 実装とテストが入った。SPEC も更新済み |
| 置き換え（→ NNNN） | 後の設計書で方針が変わった。本文はそのまま残す |
| 却下 | 採用しなかった。理由を残すために消さない |

採用後に追記してよいのは、状態の更新・未決事項の解決・誤記の訂正だけ。追記には日付を付ける。

## 共通の章立て

各設計書はこの順で書く。該当しない章は「なし」と書いて残す。

1. **状態・日付** — 状態、作成日、関連する設計書・SPEC の節
2. **背景と目的** — 何が問題で、何を達成したいか
3. **決定** — 結論を先に、箇条書きで。読んだ人がすぐ動ける形にする
4. **全体像** — ASCII 図（データの流れ、ファイル構成、モジュールの関係）
5. **詳細** — 形式・規則・関数名とシグネチャ・生成物の具体例・エッジケース
6. **選ばなかった案と理由** — 長々と並べず、検討した主な案と退けた理由だけ
7. **影響範囲・移行** — 変更・新規ファイル、既存データの移行手順、デプロイの順序
8. **テスト方針** — 直す・消す・足すテストをテスト名の粒度で
9. **未決事項** — 今回決めなかったこと、ユーザーの判断待ちのこと
